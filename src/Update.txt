### ✨ **What's New: Introducing Locator Chaining**

We can now find elements that are nested inside other elements (like a button within a specific table row) using a simple, readable syntax directly in our YAML files.

The core idea is to create a "chain" of locators using the `>` symbol.

**The syntax is:** `parent_locator > child_locator`

This lets the framework find the parent first, and then search for the child *only within that parent*.

---

### 📖 **How to Use It: A Practical Example**

This is the best part: the way you write your Gherkin steps in the `.feature` file **does not change at all!** All the complexity is handled by the framework.

**Scenario:** Imagine you need to click the **"Delete"** button specifically for the user **"jdoe@test.com"** in a web table.

#### **1. Define the Chained Locator in your `elements.yml` file:**

Instead of writing a long, fragile XPath, you can now define the relationship clearly:

```yaml
elements:
  # ... your other elements

  user_table:
    # This locator finds the table row (<tr>) that has the text "jdoe@test.com"
    # Then, within that row, it finds the button with the accessible name "Delete".
    delete_jdoe_user: 'CSS_tr:has-text("jdoe@test.com") > BUTTON_Delete'
```

* **`CSS_tr:has-text("jdoe@test.com")`** finds the correct parent row.
* **`>`** is our new separator.
* **`BUTTON_Delete`** finds the button within that row.

#### **2. Write Your Gherkin Step (No Changes!)**

You use the logical names from the YAML file, just like you always have.

```gherkin
  Scenario: Delete a specific user
    Given we are on the user management page
    When we decide to remove Jane Doe
    Then we click on user_table locator delete_jdoe_user
```

The framework automatically understands the chain and performs the precise action.

### ✅ **IMPORTANT: This Update is 100% Backward Compatible**

All of your existing tests and element locators are safe. **You do not need to change any old tests.**

* Any locator in your YAML files that **does not** contain a `>` will work exactly as it did before.
* The framework has been updated to intelligently handle both old and new locator styles.
